## 1. Executive Summary

The API surface is fully wired: **every endpoint** the Flutter and React clients call
(method, URI, query params, Sanctum/phase gates) matches `routes/api.php` — this
re-verifies the 2026-09-11 conclusion against the current `auth` branch. Request
bodies align with all five form-request validation classes, and both clients handle
401/419 correctly.

However, four issues remain and one is new since the last review:

- 🔴 **Base URL drift** (new): clients + server `.env` still point at
  `https://100.84.115.25:8000`, not the stated backend `https://debian.tail7e9e1e.ts.net`.
- 🔴 **`Results.jsx` never renders the real API response** — it falls back to
  hardcoded mock winners even though `/admin/results` is fetched successfully.
- 🔴 **Mock fallback data is presented as real** in the Flutter dashboard and
  candidates screens when the backend is unreachable.
- 🟠 **Error-state gaps**: 409 “Already voted”, 403 phase messages (React), stale
  results-provider 403s after phase flips, and an un-gated My Ballot submit button.

## 3. Payload & Model Consistency

### 3.1 Request bodies vs server validation — all consistent ✅

- **Register** sends `student_id, name, email, password, password_confirmation` →
  matches `StudentRegistrationRequest` (`confirmed`, min:8, `[a-z]/[A-Z]/[0-9]`,
  `exists:registrar_imports,student_id`, `unique:users,email`). Client-side
  validators mirror the same rules.
- **Candidacy** sends `position_id, platform_statement, certify:true, slogan?, party_name?`
  as `multipart/form-data` → matches `CandidateApplicationRequest`
  (`exists:positions,id`, max:5000, `accepted`, photo `image|mimes:jpg,jpeg,png|max:5120`).
  `photo` is supported server-side but the current screen does not offer upload — optional, not a bug.
- **Ballot draft** `PUT /ballot/me` sends `{ selections: { slug: ref | [refs] } }` →
  matches `BallotController::saveDraft` (`selections` array), stored as JSON.
- **Vote submit** `POST /ballot/me/submit` (and unused `POST /vote`) sends the same
  shape; `VoteController::resolveSelections` accepts scalar-or-array per position,
  validates refs against **approved** candidates per position, and enforces
  `seat_count`. Flutter already caps multi-select choices client-side (Senator = 12).
- **Admin status PATCH** sends `{ status }` with values `pending|approved|rejected` →
  matches `UpdateCandidateStatusRequest`.
- **Election config PUT** sends `title / phase / registration_opens_at /
  voting_closes_at / positions[{slug, active}]` → all fields present in
  `ElectionConfigRequest` (phase enum, dates, `after_or_equal` close≥open).
- **CSV import** posts a `file` field → matches `RegistrarImportRequest`
  (`mimes:csv,txt`, ≤10 MB). Client-side preview parsing is harmless duplication.
- All 9 Flutter models parse both `snake_case` (actual wire shape) and `camelCase`
  (legacy), plus `{user:…}` and `{results:[…]}` container unwrapping.

## 4. Error Handling & State

### 4.1 Solid ✅

- **401** — Flutter Dio interceptor → `AuthEvent.unauthorized` → logout + token wipe
  (correctly excludes `/auth/login` and `/auth/register`). React clears session and
  resets the CSRF cache on both `401` and `419` (token mismatch after
  `session()->invalidate()` / `regenerateToken()`).
- **422** — both clients surface Laravel’s top-level `message`.
- **429** — rate-limited login surfaces “Too many attempts…” with `Retry-After` in both clients.
- **Connection failures** — Flutter auth shows “Cannot reach the API server…” instead of a bogus “Invalid credentials”.

### 4.2 Gaps

| # | Severity | Issue | File | Effect |
|---|---|---|---|---|
| 1 | 🔴 | **Mock fallback data shown as real.** On API failure the dashboard fabricates turnout (1,250/1,500/840) and the candidates/positions providers return fake students.
